# TODO-check

## 這個 skill 在做什麼

`life-record-docs/back-TODO.md` 是這個專案(life-record-api)的 TODO 清單,裡面記的是「之後要做/要修的事」,但清單本身不會自動反映程式碼有沒有真的改過。這個 skill 的工作是幫使用者「對帳」:把清單裡的每一項,拿去跟目前的原始碼實際比對,看看是不是已經被解決了,而不是靠記憶或用猜的。

## 步驟

1. **讀取清單**:讀 `/Users/fei/code/life-record-docs/back-TODO.md` 的完整內容,列出裡面每一個獨立的項目(通常一個標題段落或一個條列項目算一個獨立的檢查項目)。

2. **逐項比對程式碼**:針對清單裡描述的每一項,去讀這個 repo(`life-record-api`)裡相關的檔案來確認現況。清單裡通常會直接點名檔案路徑或函式名稱(例如 `src/life_record_api/services/accounting/records.py` 的 `insert_record`),優先直接去讀那個檔案;沒有明確點名的話,用 grep/搜尋關鍵字(函式名稱、變數名稱、關鍵字串)找到對應的程式碼段落,不要用猜的。確認:
   - 清單描述的問題/待辦事項,現在的程式碼是不是已經處理掉了
   - 如果清單裡有明確的判斷依據(例如某個特定做法、某個判斷順序),對照程式碼目前實際的寫法是否吻合
   - 看不出來的話,誠實回報「不確定」,不要硬猜一個答案

3. **回報結果**:用清單方式回報每一項的判斷,格式:

   ```
   ✅ 已完成:<項目摘要>
      理由:<指出具體對應到哪個檔案/哪段邏輯,為什麼判斷是完成的>

   ⬜ 還沒處理:<項目摘要>
      理由:<現況是什麼,還缺什麼>

   ❓ 不確定:<項目摘要>
      理由:<看不出來的原因,建議使用者自己確認的地方>
   ```

4. **絕對不要自己去改 `back-TODO.md`**——不打勾、不刪除項目、不重寫這份檔案的任何內容。這份檔案是使用者自己維護的紀錄,使用者說了要自己手動勾選,這個 skill 的角色只到「回報」為止,不做任何寫入動作。

## 為什麼要這樣做

`back-TODO.md` 裡很多項目是「已知限制,先不處理」「之後有空再看」這種需要主動回頭確認的事,光靠使用者自己記憶容易忘記哪些已經處理過。用程式碼實際狀態去交叉比對,比單純問「這個做了嗎」更可靠,而且回報時附上具體的檔案/理由,讓使用者自己判斷、決定要不要勾選,而不是盲目相信一個沒有根據的答案。
